## 结论

**v0.1.8e 已真实生效,且修复了 v0.1.8d 的核心结构矛盾。** 上一轮(v0.1.8d §6.3)的结论是「目录掩码 presentation-only,被掩的 `skill` 在 `both` 模式下模型直调照样执行」;本轮 D1 改用 registry 级 `restrict({deny})`,把掩码从「摘广告」升级为「摘通路」——**被掩名对 LLM 全链路消失**(wire 直调面 + 目录 + REPL 绑定 + 按名 dispatch 五面一致)。这条链在本会话每一格都实证成立。

8 项决策的落地结果:**D1/D2/D3/D4/D6/D7 全过,D5 部分达成,D8 三设备两通一断**。另发现 **3 处设计文档/实现漂移** 和 **1 处部署缺陷**(browser 设备缺 `@puppeteer/browsers` 依赖,运行时拉不起来)。

## 2. D1 注册表掩码(核心,全过)

deny 名单 9 名:`skill` / `send_message`(上游)/ `report` / `list_agents` / `subagent` / `subagent_fork` / `interrupt_agent` / `workflow` / `ralph`。

**2.1 REPL 绑定面(硬门)**:8 个非桥名全部 `ToolCallError: unknown binding "tool.<name>"`:

```
skill / report / list_agents / subagent / subagent_fork /
interrupt_agent / workflow / ralph
  → ToolCallError: unknown binding "tool.<name>"
```

**2.2 wire 直调面**:我的直调函数集(22 个平坦名 + `eval` + 5 个 MCP 名)中,上述 9 名**一个都不在**。与 v0.1.8d 对照——上一轮 `skill` 还在 wire 上、模型直调可达(L1B 放行);本轮 `skill` 从 wire 消失。这是本次改动对 v0.1.8d 结构矛盾的正向修复,直接实证。

**2.3 能力保留靠桥,不靠 registry 豁免**:`read skill://grilling` 正常返回技能正文(skill 能力经 URL 桥保留);own 层 wrapper(`read`/`write`/`grep`/`glob`)全程不受 deny 影响(§6/§7 的每一步都靠它们完成)。

## 3. D2/D3 桥 + REPL 自动映射(全过,含 1 处命名漂移)

**3.1 `send_message` 桥(单向实测全过)**:桥以 `send_message` 为名,`receiver: 'child' | 'parent'`:

- `receiver='parent'`(root 无父)→ 结构化 `{error: '...only a live continuable child agent can report to its parent (a root agent has none) — agent "session-…" is no…'}`(服务层 `authorizeReporter` 的 UNAUTHORIZED 被桥如实转译,不崩溃)。
- `receiver='child'` 缺 `subagent_id` → 结构化 `{error: 'send_message() receiver "child" requires {"subagent_id": "..."}'}`。
- `receiver='sideways'` → 结构化 `{error: 'unknown receiver "sideways"'}`。

**3.2 REPL 绑定单态自动映射**:绑定集 = restrict **之后** `registry.schemas(agent)` 的平坦可见名全集。实测 22 名(与 wire 平坦名一一对应,无名单、无二态):

```
memory_search, memory_add, memory_list, memory_flush, bash, glob, grep,
job_output, job_list, job_kill, ask_user_question, web_search, read, write,
edit, read_image, todo_write, get_goal, create_goal, update_goal,
exit_plan_mode, send_message
```

被掩名随投影消失自然不绑(§2.1);MCP 非平坦名 `mcp__cordis-a2a__*` → `unknown binding`(如实跳过)。

**3.3 命名漂移(design vs 实现)**:design D1/D2 与 proposal 都把桥命名为 **`agent_message`**;实现与部署的桥名是 **`send_message`**(复用上游同名,`receiver` 参数区分方向)。功能语义与设计一致(child 下行/parent 上行、root 无父结构化拒绝),但**桥名与文档不符**——要么改名实现,要么回写文档。

## 4. D4 目录段 = REPL bridge instructions(全过)

部署形态 = **选项 B(signatures)**:`REPL_BRIDGE_CATALOG_MODE = 'signatures'`。我看到的目录段就是「`tool.<name>(args: {…}) -> <output>` 每工具一行」的 omp 式紧凑签名,保留输出契约,无逐工具参数 interface 块,无 REPL 可调清单。

## 5. D5 run_code = REPL scripting pad(部分达成,含 "kernel" 泄漏)

- `eval` 工具描述:"Execute one Python cell on a session-persistent **scripting pad**…" ✓ 无 kernel。
- 桥说明段(目录):"session-persistent **scripting pad** (Python today…)" ✓ 无 kernel。
- **但 `dashr:control-prompt` 段(order 100)仍 3 次使用 "kernel"**,且逐字渲染给我:

```
"one `eval` call runs one Python program on a persistent IPython kernel"
"everything else stays in the kernel"
"they live in the kernel subprocess: keep durable state in files"
```

设计 D5 的原话是「LLM 可见文案**不用 kernel 一词**」。目录段做到了,`control-prompt.md`(另一个 LLM 可见段)没做到。另:旧渲染器 `renderToolsSdkPy`/`SDK_INSTRUCTIONS` 在 `py-sdk.ts` 里仍满篇 "kernel",但它是**死代码**(index.ts 只 import `renderReplBridgeInstructions`),不达模型,风险为零。

## 7. D7 RAM 物化 = /dev/shm(全过,路径直接实证)

content-backed 搜索的物化根目录从 `/tmp` 切到 `/dev/shm`,并 `finally` 清理。**grep 返回的真实路径直接落在 tmpfs**:

```
grep ctx://model  → 匹配路径 /dev/shm/dashr-url-ZILDQp/content.txt
grep agent://     → 匹配路径 /dev/shm/dashr-url-5w99JR/content.txt
```

## 8. D8 dvc 设备(三设备两通一断)

**8.1 名册**:裸 `dvc://` 返回 4 设备(不再是 `no devices mounted` 占位):

```
ast_edit  AST-aware structural rewrite: {ops: [{pat, out}], paths: string[], dryRun?: boolean}
ast_grep  AST pattern search: {patterns: string[], path?, offset?, limit?, includeMeta?}
browser   headless Chrome via puppeteer-core — open {url} / run {code|goto,type,click} / close
lsp       LSP queries over stdio language servers — diagnostics / definition / references / hover
```

`dvc://<device>` 返回一行摘要 + `usage: write dvc://<device> …`;`dvc://nonexistent` → `unknown device: …`。

**8.2 ast_edit / ast_grep(通)**:`@oh-my-pi/pi-natives` npm 包装的直 dlopen 在本机 linux-x64 成功。

- `write dvc://ast_grep {"patterns":["add($A,$B)"],"path":…}` → 结构化 matches(命中 `add(1, 2)` @ line 4,带 byteStart/startLine/startColumn)。
- `write dvc://ast_edit {ops:[{pat,out}], paths:[…]}`(dryRun 默认 true)→ 结构化 changes 预览,`applied: false`,文件内容原样未动。

**8.3 lsp(优雅降级,符合预期)**:`diagnostics` 请求 → 结构化 `language server binary "typescript-language-server" not found — npm install -g …`。二进制缺失时如实报缺、不崩溃,符合 D8 spec。

**8.4 browser(断,部署缺陷)**:`open` → 结构化 `dvc:// device "browser" execute failed: puppeteer-core is not installed … Cannot find package '@puppeteer/browsers' imported from …/puppeteer-core/lib/puppeteer/node/ChromeLauncher.js`。定位:**`puppeteer-core@25.3.0` 已装,但其传递依赖 `@puppeteer/browsers@3.0.6` 缺失**(profile `web` 的 node_modules 顶层与嵌套均无)。系统 Chrome 在,`run`/`close` 的「无页可跑/无可关」状态机也正确——**唯一断点是依赖未装全**,与 omp patch 无关(design S6 已裁决无 patch 可冒烟)。属部署收尾遗漏,非代码缺陷。

## 9. 与设计文档的偏差汇总

1. **桥名漂移(D1/D2/proposal)**:文档 `agent_message` vs 实现 `send_message`。语义一致,名称不符。
2. **D5 "不用 kernel" 未全达成**:`control-prompt.md` 3 处 "kernel" 逐字渲染给模型;`renderToolsSdkPy` 旧渲染器仍含 "kernel"(但为死代码,不达模型)。
3. **D3 "`dir(tool)` 自查" 承诺落空**:桥说明段写「read the live member set at run time with `dir(tool)`」,但 `dir(tool)` 返回**空**(惰性 `__getattr__` holder 无 `__dir__` 覆写,`hasattr` 对任意名恒真)。真实绑定集只能靠未文档化的内部 `__dashr_injected__`(bootstrap 写入的 spec,`functions` 为 22 名列表)或 wire/目录声明得知。要么给 holder 加 `__dir__`,要么改说明措辞。
4. **host 静态 prose 与掩码面残留不一致**:host 基础提示里仍有「Use the workflow tool ONLY when…」「Use the ralph tool ONLY when…」等措辞,而 `workflow`/`ralph`/`subagent` 已被 deny 掩码从可调面摘除。这是 registry 掩码无法触达的宿主静态文案(design Risks 的「restrict 名单漂移」同源),非 DASHR 缺陷,但模型会读到「用某工具」却调不到它。

## 10. 建议

1. **browser 收尾**:在 profile 安装 `@puppeteer/browsers@3.0.6`(或让 puppeteer-core 走完整 `npm install`),重新冒烟 `open`/`run`/`close`;否则 D8 的 browser 设备形同虚设。
2. **桥名二选一**:把实现桥名改成 `agent_message`,或回写 design/proposal 的 D1/D2 为 `send_message`。当前文档与部署名不一致,会让后续 reader 误解。
3. **D5 收尾**:`control-prompt.md` 的 3 处 "kernel" 改成 "scripting pad"(或 "pad"),并顺手清理 `renderToolsSdkPy` 死代码里的 "kernel" 措辞,避免误当仍在用。
4. **D3 收尾**:给 `_DashrBindingHolder` 实现 `__dir__`(返回 `functions` 键集),或把桥说明里的 `dir(tool)` 提示改为「绑定集见上方 Tool declarations / wire 声明」。
5. 无需回滚。本轮无阻断性缺陷;deny 掩码是 v0.1.8d 结构矛盾的正确解法,已实证生效。
