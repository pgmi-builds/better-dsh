## 0. 结论摘要

| 验收面 | 结果 | 一句话 |
|---|---|---|
| URL resolver + read 路由 | ✅ 生效 | `read` 能把 `scheme://` 分流到 handler |
| `skill://` | 🔴 坏 | `ctx.skills` 注册表空，与 prompt 里的 skill 目录不同源 |
| `agent://`（名册 / 输出 / transcript / child） | ✅ 生效 | 四形态返回真实内容；但名册字段与 spec 不符 |
| `history://` 并入 `agent://` | ✅ 生效 | 返回「已并入」提示 |
| `dsh://config` | ✅ 生效 | 返回 resolved settings，无 secret 泄漏 |
| `dsh://docs` | 🔴 坏 | `docs/` 没打进发布包，`resolveDocsDir` 从安装路径向上找不到 |
| `ctx://` 读 | 🔴 坏 | URL 分支传空 env，落到 `AGENTLESS_KEY` 空内核 |
| `ctx://` 写 | 🔴 未接线 | `writeCtxVar` 是死代码，`defaultSchemeWrite` 直接抛不支持 |
| `xd://` 读 + 写 | ✅ 生效 | 空占位行为与 spec 一致 |
| selector 语法（`:N-M` / `:raw` / …） | ✅ 生效 | `dsh://config:1-3` 正确按行截断 |
| 未注册 scheme 报错 | ✅ 生效 | 结构化报错并列出 `registered: agent, ctx, dsh, skill, xd` |
| mask `skill` 工具（D5） | 🔴 未生效 | 只挡 REPL 的 `tool.*` 面，host 层原生 `skill` + `<available_skills>` 仍在 |
| **`write` 普通路径（透传）** | 🔴 **回归** | **`write` 工具对工作区任意路径一律拒绝，只放行 `/tmp`；`read`/`edit`/bash 均正常** |

**净结果：6 个 scheme 里 3 个半生效（agent / dsh:config / xd + selector/history），2 个半坏（skill / ctx 读），1 个彻底坏（ctx 写），1 个配套改造（dsh:docs）坏，1 个 BREAKING（mask skill）未生效；另有 1 处**非 URL 路径 `write` 的回归**（破坏「普通路径透传」spec）。**

## 3. 失效点根因（已定位到源码）

1. **`skill://`** —— `dashr/src/url-schema/handlers/skill.ts` 查 `ctx.skills.get(name)`（`@deepseek-ai/dsh-skill` 的 `SkillRegistry`），但该注册表**为空**，与注入 prompt 的 harness session skill 目录（`<available_skills>`）不是同一来源。skill handler 本身逻辑正确（错误分支、`/path` 资源寻址、路径逃逸守卫都在），只是上游 `ctx.skills` 没被喂进实际可用的 skill。

2. **`dsh://docs`** —— `dashr/src/url-schema/index.ts` 的 `resolveDocsDir()` 从 `import.meta.url` 向上找 `docs/`。发布包 `@pgmi-builds/dashr` 里**没有 `docs/`**（`docs/` 在仓库根 `/home/u1/workspaces/dashr/docs`，位于包根 `dashr/` 之外，未进 npm 包）。运行时从 `~/.dsh/profiles/web/node_modules/...` 加载，向上走到 `/` 也够不着仓库里的 docs。dev 布局（`dashr/lib/index.js` 向上能到 `/home/u1/workspaces/dashr/docs`）能跑通，装进 node_modules 就断——纯打包缺口。

3. **`ctx://` 读** —— `dashr/src/url-schema/tools/read.ts` 的 URL 分支调 `resolver.resolve({}, rawPath)`，传**空 env**；`handlers/ctx.ts` 随之 `queryVar(name)` 不传 `principal`，`runtime.ts:393` 落到 `AGENTLESS_KEY`（共享默认内核）——而 eval cell 跑在**会话 principal 键**的内核上。所以永远读一个没人用的空内核，真实存在的变量也报 missing。对比：文件分支正确用了 `execSessionKey(exec)`，URL 分支没传。

4. **`ctx://` 写** —— `dashr/src/url-schema/tools/write.ts` 的 `defaultSchemeWrite` 对除 `xd` 外一律抛 `URL_WRITE_UNSUPPORTED`；`handlers/ctx.ts` 里已写好的 `writeCtxVar` 是**死代码**（`index.ts` 装 write 工具只传 `{ nativeWrite }`，没传 `writeScheme` 把 `ctx://` 路由到 `writeCtxVar`）。

5. **mask `skill`（D5）** —— `dashr/src/index.ts:154` 的 `MASKED_TOOL_NAMES` 确实含 `'skill'`，但它只作用于 REPL 自己的 `tool.*` 绑定面（`index.ts:761`）+ Tool Catalog（`index.ts:901`），所以 eval cell 里 `tool.skill` 确实没了；但**挡不住 host 层注入的原生 `skill` 工具 + `<available_skills>` 目录**，模型从原生工具面照样能看见并调用 `skill`。验收项「工具目录不含 skill」未达成。

6. **`write` 普通路径回归（新增）** —— 设计 D2 明确「不替换 write（write 保留原生，只挂 write-hook 装饰结果）」，但 v0.1.10 实际用 `tools/write.ts` 的 `createWriteTool` 以 `name: 'write'` **shadow 了原生 write**，其 `nativeWrite` 直接 `ctx.fs.resolve(...)` + `ctx.fs.writeText(...)`，**没走原生 write 工具的 write-intent 政策门**，于是对工作区路径被 sandbox 拒绝（`file access denied under workspace-write mode`），只放行 `/tmp`。对比：`read`/`edit` 走 vendored hashline 的 fs-bridge（含 `fs/write-intent` + `fs/observed` 政策门），工作区读写正常；bash 也正常。**这直接违反 spec「普通路径透传」——非 scheme 的 `write` 行为与引入 URL schema 之前不一致。**

## 4. 一处 spec 偏差（非阻断）

`agent://` 名册 schema 与 spec 不符：

- `specs/agent/spec.md` 要求：`id / status / kind / parent / last activity`
- `handlers/agent.ts` 的 `renderRoster` 实际：`id / origin / depth / cwd`

字段语义对不上（`origin`≠`kind`、`depth`≠`parent`、缺 `status`/`last activity`、多了 `cwd`）。
