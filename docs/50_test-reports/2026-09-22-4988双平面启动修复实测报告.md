## 三、根因链（每步有实证）

1. **崩溃点**：`agent-loop/src/tool-calls.ts` `startCall` 的 `ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec)`。栈经临时诊断打点捕获（已还原）。`tool/call` 事件先落（`appendToolCall`），prepare 抛 TypeError → turn 以 UNKNOWN 结束；**孤儿 tool/call 无结果** → 之后每轮 DeepSeek 序列化器拒绝（`llm-deepseek/src/protocols/messages/serialize.ts:117` 的 "tool calls need immediate results"）。
2. **诊断打点实测**：`ctx.tools` 是 ToolRuntime 实例，ownSymbols 含 `Symbol(@deepseek-ai/dsh-tools.scheduler)`，但与 agent-loop 导入的 symbol **同 description 不同对象** = 同进程两份 `@deepseek-ai/dsh-tools`。
3. **两份从哪来**：tsx 源码启动 = 双平面运行时——
   - TS 文件（apps/cli、各包 src）经 `tsconfig.base.json` `paths`（`@deepseek-ai/dsh-*` → `packages/*/*/src/index.ts`）→ **src 副本**；
   - plugin loader 把组合行模块名解析为构建 lib 的 file URL → **lib 副本**（且 vendor/cordis 的 lib bundle 陈旧——不含 `FiberState` 导出）。
   - lib 侧 ToolRuntime 把 scheduler 挂在 lib 副本 symbol 下；src 侧 agent-loop 按 src 副本 symbol 查 → `undefined`。
4. **为何 prepare 门不接住**：`prepareExecution` 的 try/catch 只包门内瀑布；`ctx.tools[SYMBOL]` 在 agent-loop 侧、门之前求值。
5. **为何 paths-less 收敛不可行**：`vendor/cordis/src/fiber.ts` 的 `export const enum FiberState` 被 tsc 内联（bundle 无该运行时导出），tsx 只能保留 value import → 产物 lib 面 boot 必然 `SyntaxError: ... does not provide an export named 'FiberState'`。**源码启动本质上需要 src 面** → 唯一正解 = 产物面启动。
