# v0.2.4-d `dashr-web-password` 密码门（token → password）实测报告

日期：2026-10-01
组件：`better-dsh/web-password`（新 row `dashr-web-password`），dev 版本 `0.2.4-d`
裁决来源：user 直接指令 —— 「take the native cookie minting, only replace the pw for token url, i.e. 30 days cookie expiry, ask user for pw again to mint cookie」＋「credential store, default, hash of "admin", dun invent a pw setup step」

---

## 一、要解决的问题与结论

原生 `dsh web` 的门是一枚 **per-boot 的 `?token=` URL**：它只负责首铸一枚 30 天签名的浏览器 cookie，之后靠 cookie 通行（`$DSH_HOME/.credentials.yaml` 里的 `client-connection/browser-session` 是签名密钥，持久）。

user 要求：**把这扇门换成密码**，cookie 仍用"原生的那一套"（同样的密钥、同样 30 天）。

结论：**可行，且无需改动任何上游代码。** 关键裁决 ——「整个子包 patch 掉」不成立：`@deepseek-ai/dsh-client-connection` 1493 行里认证只占一个 311 行文件（`browser-auth.ts`），其余是 RPC 载体 / `/api` 桥 / trust fence；而它的 row 同时供养浏览器半边（`dsh.client`），换 row name 会连带干掉前端传输。真正的缝不在包，在**路由表**与**cookie 规范的公开性**：

1. webserver dispatch = `exact` → longest `prefix` → `fallback`（`packages/host/webserver/src/index.ts:318`），而 **exact `/` 上游无人占用** → 我们拿下。
2. 页面侧的唯一鉴权点是 fallback owner 里的 `ctx.connection.authorizeIndex`，而 `?token=` 兑换**只在 `pathname === '/'` 分支存在**（`browser-auth.ts:238`）。占了 `/`，token 门自然退休。
3. `/index.html`、`/api` 与其余路径继续走原生校验器；我们铸的是**同规范、同密钥**的 cookie，原生校验器直接放行。唯一的例外是 `/` 本身：cookie 有效时由本插件**用上游自己的 dist 解析器渲染同一份 index**（见下 §二 的二次修订），所以登录后 URL 停在 `/`，不产生任何跳转。

## 二、改动点

| 文件 | 性质 |
|---|---|
| `better-dsh/src/web-password.ts` | 新增（~640 行，host-only 插件，无 client 半边） |
| `better-dsh/test/web-password.spec.ts` | 新增（14 例；**用上游真实 `BrowserAuth` 类做 oracle**，非自证） |
| `better-dsh/cordis.patch.yml` | 新增 1 条 insert 行 `dashr-web-password`（Plugins 页可独立开关的组件） |
| `better-dsh/tsdown.config.ts` · `package.json` | 新 subpath entry `./web-password`；peer `dsh-credentials` / `dsh-host-webserver` |
| `@deepseek-ai/*` 上游 | **零改动**（这是本方案的全部意义） |

密码本身是插件自己的 credential record `dashr-web-password/passphrase`：`{version:1, algorithm:'scrypt', salt, hash, N:16384, r:8, p:1, keylen:32}`。**首次激活若无记录就自动播种 `scrypt('admin')`** —— 零设置步骤，开机即用。改密码 = 替换该 record（无 UI / 无 CLI，user 明令不发明设置步骤）。

流程：`GET /` 无有效 cookie → 服务端渲染密码表单；`POST /` 校验通过 → 铸**原生格式** cookie（`dsh-auth-<b64url(sha256(authority))>`，`v1.<b64url(json)>.<b64url(HMAC-SHA256)>`，`Max-Age/Path/Expires/HttpOnly/SameSite=Strict` 与原生逐字一致）→ `303 /`。带 cookie 的 `GET /` 由本插件直接渲染 SPA index（dist 锚点取自 `@deepseek-ai/dsh-web-app` 导出的 `internals.resolveDistIndex()`，即上游 fallback 自己用的那个函数；`<base href="./">` 插入与 `host-frontend-static` 逐字一致），**零跳转，URL 保持 `/`**。连续 6 次失败起按 peer 指数退避（上限 60s，429 + `Retry-After`）。

> 二次修订（2026-10-01，user 反馈「登录后 URL 不该变成 /index.html」）：初版是 `303 /index.html` 借原生 fallback 出页面，代价是 URL 脏。现在改为在 `/` 原地渲染，`/index.html` 不再是流程的一部分（直接访问仍由原生放行，不做重定向）。dist 锚点一旦解析失败（例如上游不再导出 `internals`），本插件**降级**回 `303 /index.html` 而不是 503 —— 只有渲染这一环失败，认证本身完好。

## 四、已知边界 / 未做

1. ~~登录后 URL 是 `/index.html`~~ —— 已修（见 §二 二次修订）：登录后 URL 就是 `/`，`/index.html` 不再出现在流程里。
2. **host 日志在本 composition 下不打印**（`ctx.logger('dashr-web-password')` 的 info/warn 没进 rig 日志——原生 web composition 只输出 URL 行）。失败诊断因此写进 503 响应体（自包含文案），日志调用保留（换 composition 仍有效）。
3. **密码明文过 HTTP**：user 明确裁决 —— 本地/LAN，公网走 HTTPS，不再是问题。
4. **`?token=` 链接仍在启动时打印**（`web-runtime` 的 `printUrl: true`），但它现在只把人带到密码页。刻意不改：省一条 patch，且打印的 URL 仍然可用（只是多一步）。
5. **未发 npm**。按本仓红线，发布需 user 单次明确放行；本次仅 dev 版本 `0.2.4-d` + rig 物理安装。
6. **未改上游任何文件**；回滚 = 在 profile 用户层给 `dashr-web-password` 行写 `{disabled: true}`（原生 Plugins 页 toggle 即可），或退回 `0.2.4-c`。
7. **新增一处上游耦合（有意的，且降级安全）**：`/` 的 index 渲染依赖 `@deepseek-ai/dsh-web-app` 导出的 `internals.resolveDistIndex()`。选它而不是自己拼路径，是因为 dist 锚点属于该包的装配事实（它从已安装的 `@deepseek-ai/dsh-web-frontend` 推导），复制一份必然随上游漂移。上游若删掉该导出，本插件不会崩——降级回 `303 /index.html`（旧行为），只是 URL 又脏一次。新增 peer：`dsh-web-app`（optional，懒 import，非 Web composition 不触达）。

## 五、操作备忘（给下一位）
