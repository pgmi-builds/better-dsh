## §2 裁定：fs reach 的两个平面（用户裁定 + 推理确认）

- **平面 A —— 被认可的工具面**：cell 内 `tool.*` 与 agent 原生工具调用走**同一条 bridge → tool-service 路径**（同一校验/掩码/策略/日志，auto-bridge 机制见 `src/bridges/index.ts`）。read/write 等原生工具**本就持真实 fs**——它们的收窄（workspace-write、mask）来自工具面的策略层，不是虚拟化。
- **平面 B —— 解释器裸达**：cell 内裸 Python（`open`/`os`/`shutil`/…）以内核进程身份执行，达 = host 用户（u1/1000）的达。
- **裁定 ①**：「内核有 host-user fs reach」**在 REPL 使用场景本来就是如此**——交互式 IPython/Jupyter 内核即以启动用户身份运行、持其全达；better-dsh 供给受管 venv 内核 = 「用户的 Python REPL」，未做 OS 级逐调用沙箱是 REPL 的固有语义，**不是插件开的洞**。此前把这点标为 caveat 的措辞收回。
- **裁定 ②**：本 agent 运行场景中 eval 只是 agent 的工具之一；原生工具本就有真实 fs 达 → 内核达相对工具套件**不是异常**。因此 **eval 的强制边界 = 平面 A（工具面）+ 掩码/策略，不是平面 B（解释器）**。
- 推论：安全评审/对齐评审不应把 B 平面裸达记作 sandbox escape 缺陷；若 alpha.5 侧期望 run_code OS 级逐调用受限，**有状态持久内核无法廉价满足**（逐调用沙箱与驻留状态互斥）——是设计取舍而非缺陷（关联 `10_plans/dashr-blueprint.md` phase 2 fork-server 复用父内核状态的方向）。

## §3 沙箱后端环境观察（非插件缺陷）

### 5.2 C2/O-1 关闭：沙箱后端缺失根因 = 嵌套沙箱，非构建、非上游

- **复现**：在 agent 沙箱化 bash 内执行 bwrap 功能探测（`packages/sandbox/sandbox-local` 的 `defaultProbeBwrap` 同形命令）→ `bwrap: No permissions to create a new namespace`（exit 1）。前一代 4999 daemon 正是从沙箱化 bash 后台任务启动的——daemon 继承沙箱环境，自身再 spawn bwrap 即嵌套，探测必败 → `SANDBOX_UNAVAILABLE`（bwrap/Landlock/…全判缺）。
- **对照解释**：v0.2.1d 期实例的 daemon 启动自非嵌套上下文 → 探测通过、bash 可用。上游 alpha.5 的 workspace-write 沙箱本身无恙；我们的 build 也无恙。
- **修复**：daemon 改经 `systemd-run --user` 启动于沙箱之外（unit `dsh-4999-test`，与 prod 的 systemd 形态对齐；stdout/stderr 落 `.scratch/dsh-4999.log` 取 token）。当前 token：`qzwIUV1nwVsixUfW8sa-sgodW8uSQAyCzi7XHtflfAc`。**验收建议**：在 4999 开 session 跑任意 bash 命令（如 `pwd`）——应正常沙箱执行而非 `SANDBOX_UNAVAILABLE`。
- **约定固化**（AGENTS.md 已更新）：agent 从沙箱会话重启 4999 一律走 systemd-run --user；勿从沙箱化 bash 直接拉 daemon。
