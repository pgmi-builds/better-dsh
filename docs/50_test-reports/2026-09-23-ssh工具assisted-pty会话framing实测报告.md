## 二、会话机制解剖（关键，后文所有行为都由此解释）

远端进程树（`ps -o pid,ppid,cmd -p $$ -p $PPID`，dev4）：

```
    PID    PPID CMD
1169518 1169458 sshd: u1@pts/1
1169728 1169518 bash --rcfile /tmp/.better-dsh-rc-6e1e345f3a3e4493
```

rcfile 全文（`/tmp/.better-dsh-rc-<hash>`，两个 target 上内容一致）：

```bash
# dashr engine rcfile — generated by dashr/remote/framing, do not edit.
for f in ~/.profile ~/.bash_profile ~/.bashrc; do [ -f "$f" ] && . "$f"; done
stty -echo 2>/dev/null || true
PS1=''
PS2=''
PS0=$'\033]133;C\007'
PROMPT_COMMAND='printf "\033]133;D;%s\007" "$?" ; printf "\033]7;file://%s\007" "$PWD"'
export TERM=dumb
```

由此可判定的机制事实：

1. **传输是真正的 pty**（`tty` → `/dev/pts/N`，`test -t 0/1/2` 全 yes；`stty -a`：38400 baud、40×120、canonical、`intr=^C`、`erase=^?`、`eof=^D`），不是 `bash -lc` 无 tty 管道；
2. 会话是**单条常驻交互 bash**（跨调用 PID 不变），命令由 pty 送入、以 `PS0` 的 **OSC 133;C** 起帧、以 `PROMPT_COMMAND` 的 **OSC 133;D;<exit>** 收帧；**exit code 来自终端字节流解析**，不是 ssh 的 channel exit-status；
3. **cwd 来自 OSC 7**（`file://$PWD`），`ssh({target})` 状态行的 `cwd:` 即此；
4. `stty -echo` 关回显（所以 `stdin` 参数喂入的内容不会在输出里出现）；`PS1=''` 保证无提示符噪声；`TERM=dumb` 抑制分页/颜色协商。

⚠️ 状态行自称 `env: login-shell (bash -lc)` 与实测不符——实际是**交互式 bash + 生成式 rcfile**（rcfile 内手动 source 了 `~/.profile ~/.bash_profile ~/.bashrc` 来模拟 login 语义）。属文案偏差，非功能缺陷。

## 三、缺陷 / 风险（按严重度）

### 3.1 🔴 OSC 133;D 注入：远端输出可伪造 exit code 并吞掉 stdout

命令自身只要往 stdout 写 `ESC ] 133 ; D ; <n> BEL`，就会被 framing 当作**本命令的结束标记**：

| 命令 | 观测结果 |
|---|---|
| `printf '\033]133;D;99\007'` | `[exit 99]`，stdout 为空（后续 `echo after-osc133-spoof` 被吞） |
| `echo before-marker; printf '\033]133;D;55\007'; echo after-marker; false` | 输出仅 `before-marker`，`[exit 55]`（**真实 exit 为 1，被覆盖**） |
| `printf 'MID\033]133;D;66\007TAIL\n'; echo end` | 输出仅 `MID`，`[exit 66]`（**行中位置同样生效**） |

影响：任何远端程序/日志/被下载内容里的这一个字节序列，都能让 agent 得到**假失败或假成功**，并让 stdout 在注入点被截断（静默丢证据）。dev4 与 ctr-1 均复现（ctr-1 实测 `[exit 88]`）。这是本报告唯一建议**优先修**的项。

对照：**OSC 7 注入不生效**（两条独立实证，见 §四.3）——即同一套 framing 对两类 OSC 的信任度不一致，说明「只认自己发的 marker」这件事是**可做到的**，133;D 侧漏了。

### 3.2 🔴 `timeout` 是 SIGINT 尽力中断，不是 kill

- 超时路径经 pty 发 `^C`：`cat`（stdin 阻塞）`timeout: 3` → `[exit 130 (=128+SIGINT) · interrupted]`，3.2 s 返回，符合预期；
- 但**忽略 SIGINT 的命令能整段跑完**：`bash -c 'trap "" INT; echo ctr-trapped-int; sleep 4; echo ctr-survived-SIGINT'`，`timeout: 2` → 实跑 **4.0 s**，输出两行齐全，`[exit 0 · interrupted]`。dev4 侧同测（`sleep 5` / `timeout: 3` → 5.2 s）同样复现。

影响：挂死且不吃 SIGINT 的命令（编辑器、REPL、`trap '' INT` 脚本）**不会被 timeout 终止**，且最终以 exit 0 上报，agent 会误判为成功。

### 3.3 🟠 跨命令 stdout 污染：后台写者会混进下一条命令的输出

framing 会丢弃**命令之间**的空档输出，但**下一条命令执行期间**到达的输出会被算进该命令：

- ctr-1：调用 A `( for i in 1 2; do sleep 2; echo CTR-LEAK-$i; done ) & echo bg-launched`（瞬时返回）；调用 B `bash -c 'trap "" INT; … sleep 4 …'` 的输出里出现 `CTR-LEAK-1`、`CTR-LEAK-2` 及作业控制行 `[1]+ Done …`；
- dev4 复现：调用 A 起 `for i in 1 2 3 … echo D4-LEAK-$i`（间隔 1 s），调用 B `echo start-slow-dev4; sleep 4; echo end-slow-dev4` → `D4-LEAK-1..3` 夹在 `start-slow-dev4` / `end-slow-dev4` 之间。

⚠️ 修正一个早期结论：同测法在 dev4 上曾「看不到泄漏」，原因是**后台任务已跑完、输出落在两条命令的空档被丢弃**（时序巧合），并非免疫。凡「上一条命令留下存活的后台写者 + 下一条命令耗时」即污染可复现。

### 3.4 🟡 同 target 命令串行化（正确但会阻塞）

同一 target 的并发调用被排队（实测：`sleep 4` 调用 + 立即 `echo` 调用 → 后者 0.2 s 返回，用时互不重叠）。判别实验：调用 A 阻塞在 `read`（`timeout: 8` → 8.3 s `interrupted`），同批调用 B `echo B-INPUT-MARKER` **未被当作 A 的 stdin**、正常返回 —— 说明是**队列**而非并发共享 pty。

影响：一条挂死命令会阻塞该 target 的后续所有调用（含 `ssh({target})` 状态查询）；跨 target 并行不受影响。**不要对同一 host 并发 fan-out**，要并行就换 target 或写成一条远端脚本。

## 四、设计内行为（记录，供后续依赖/文档化）

1. **完整 shell 状态跨调用持久**（同一 bash PID）：cwd、导出变量与非导出变量、shell 函数、alias、shell 选项（`set -o pipefail` 实测跨调用为 on）、作业控制均保留 → **一次 `set -e` / `cd` / `unset` / alias 会静默影响后续所有调用**；用完须显式还原。
2. **命令为简单复合时进程即会话 shell 本身**（`$$ == $BASHPID`，PPID 为 sshd）——所以「子 shell 里的 cd」不生效、而顶层 `cd` 生效。
3. **`exit` / `kill -9 $$` 杀掉会话 shell** → 工具上报 `[exit null]`（无 exit code），随后**新建 bash**（rcfile hash 变化，dev4 累计 3 个 rcfile；ctr-1 复用同一 hash，仅 1 个——差异未解释，仅记录）；导出变量丢失；**cwd 恢复到最后一次「成功完成命令」上报的路径**：
   - 实证（ctr-1）：`cd /etc` 成功上报 → 下一条命令 `cd /var/tmp && kill -9 $$`（未上报即死）→ 恢复后 `pwd` = **`/etc`**（非 `/var/tmp`）。
   - OSC 7 伪造不改变该恢复：`printf '\033]7;file://ctr-1/usr\007'; kill -9 $$` → 恢复仍 `/etc` 而非 `/usr`；另测伪造 `/etc` 后状态行仍显示真实 `/tmp`。**对 OSC 7 的信任是收敛的**。
4. **输出截断为尾偏**：单次 338,959 chars → 只回**最后 30,000 chars**，头部丢弃，首尾均有 `truncated` 标记。（代价：把状态回显放在长输出开头会被截掉；诊断请用 `wc`/`tail`。）
5. **stdout/stderr 合并**为同一有序流（stderr-only 正常出现）；**ANSI 转义原样保留**（`1b 5b 33 31 6d…`）；**NUL 字节被吞成空格**（`printf 'x\0y'` → `x y`）→ 二进制请 base64。
6. **stdin 可用且是 pty**：`stdin` 参数对 `read` 生效（`read -r first; read -r second` 拿到两行）；裸 `cat` 无输入则永久阻塞（→ 超时 130）。
7. **后台进程存活，不阻塞返回**：`setsid` / `nohup` / 裸 `&` 三者在会话 shell 被 kill 后均存活并完成写文件；`nohup … &` 会在 home 造 `~/nohup.out`（实测后已清理）。
8. **错误面**：未知 target → `[E_UNKNOWN_TARGET]` 并列出已知 target；连接不可达 → `error : ssh connect failed: connect EHOSTUNREACH …`（ctr-1 停机时实测）。
9. 其它：`sudo -n whoami` → `root`（dev4/ctr-1 均 NOPASSWD）；emoji/CJK/heredoc round-trip 正常；`locale` 见 §五。

> 探针自身的一个坑（非工具缺陷）：在 `$( )` 里跑 `test -t 1` 会因命令替换把 fd1 接成管道而返回 false，最初误判「stdout 不是 tty」；直接在顶层测为 yes。

## 八、建议（未实施，待裁决）

1. **133;D 收帧加固**：只接受「帧内首个、且位于命令输出之后的 harness 自产 marker」不可靠；建议给 marker 加**每会话随机 nonce**（`133;D;<nonce>;<exit>`）或改用独立边带通道（stdout 之外的 fd / 文件），使远端输出无法自证结束。若不愿改协议，退而求其次：解析时**取最后一个 133;D**（`PROMPT_COMMAND` 必然在命令之后执行）可让「命令内注入」失效——但命令若在注入后自杀（`exit`）仍可绕过，故 nonce 才是根治。
2. **timeout 二段式**：SIGINT 后 N 秒未收帧即升级 SIGKILL（需 kill 远端进程组，pty 前台 pgid 可查）。
3. **污染面**：收帧后到下一 `133;C` 之间的输出应显式丢弃并计数；或在 3.3 场景下把 job-control 噪声也过滤掉。
4. **文案**：状态行 `login-shell (bash -lc)` → 改为 `assisted pty (bash --rcfile)` 之类，避免误导。
5. **文档化**（面向使用方）：状态跨调用持久、同 target 串行、尾偏截断、忽略 SIGINT 的命令不会被超时终止——这 4 条会直接改变 agent 的使用策略。

## 附录 B：通用化讨论（**非实测**，讨论稿，2026-09-23）

> user 议题：「如果所有 remote 都提供这种 assisted pty session——docker、远程机器 over websocket」。以下为基于本次实测的推演，未落地。

**收益（为什么值得统一）**：assisted pty 把「远程执行」从『一次性 `exec` 取 stdout』升级成**有状态的会话面**——持久 cwd/env、可交互 stdin、真实 tty（TUI/彩色/进度条/`sudo` 提示都可工作）、以及通过 framing 拿到的**结构化 exit code + cwd**。同一套 framing 换个 transport 即可复用，agent 侧只认一套语义（本次 dev4/ctr-1 逐项一致就是证据：framing 对 VM/容器无感）。

**成本/风险（本次已暴露的都在这里放大）**：
- **信任边界翻转**：marker 走的是**被观测对象的输出**。133;D 注入已经能伪造 exit code；一旦 transport 变成 docker daemon / WebSocket 网关这种「中间层」，多一个可注入 stdout 的位置就多一个伪造点。正解是 **nonce / 边带通道**，让「结束」由 harness 自己证明，而不是由远端输出自证。
- **生命周期归属**：pty 会话是长命进程。docker 容器重建、WebSocket 断线重连、k8s pod 漂移之后，**会话必须被判死并重建**，否则会出现「协议还对、shell 已换人」的僵尸会话（本次 `kill -9` 后 PID 变更 + rcfile hash 变更即其简化版）。需要会话身份（boot id/nonce）随帧下发，客户端校验不一致即重连。
- **状态泄漏**：持久 shell 是把双刃剑（§四.1）。容器场景下更危险——一个 agent 的 `export TOKEN=`/`cd`/alias 会跨 turn、甚至跨「逻辑任务」残留；多云多租户时这就是横向面。建议每条 framing 命令都带**可选无状态模式**（等价 `bash -lc` 语义：新 shell、显式 cwd、显式 env），把「持久」变成 opt-in 而非默认。
- **背压与串行化**：本次同 target 串行是安全选择，但 `docker exec`/WebSocket 是**天然可并发**的 channel；若照抄「一会话一队列」，长任务会互相阻塞。需要区分「会话（pty，串行）」与「命令（channel，可并发）」两层，并把强制串行限制在真的共享 pty 的那一层。
- **`TERM` 与噪声**：`incus exec`/`docker exec` 默认无 tty 且 `TERM` 缺失/继承（§六）。统一层必须**显式分配 pty 并注入 TERM**，否则 TUI 类工具在容器里行为漂移；同时 `PS1=''`+`stty -echo` 这类「消噪」也要成为 transport 契约的一部分，而不是 ssh 专属技巧。
- **窗口/尺寸与控制字符**：40×120 是本次观测到的固定尺寸。docker/WebSocket 侧需要 `TIOCSWINSZ` 协商，否则 `less`/`top`/`gdb` 一类程序布局错乱；`^C`/`^D` 语义（本次 timeout=SIGINT）也必须定义成契约，而不是各 transport 自行其是。
- **可观测性**：既然 exit code 与 cwd 都来自字节流，那么**字节流本身就是审计证据**。建议 transport 层留存原始帧（含 marker 与注入点），这样 133;D 这类事件可被事后检出，而不是静默生效。

**一句话**：assisted pty 的**语义**（有状态、可交互、结构化收帧）值得在 docker / WebSocket 上复用，但**信任模型**必须同时升级——marker 必须由 harness 用 nonce/边带自证，会话身份必须可校验，状态持久与并发必须显式可选。否则就是把 ssh 面已经暴露的三个坑（自证结束、僵尸会话、状态残留）复制到更多 transport 上。
