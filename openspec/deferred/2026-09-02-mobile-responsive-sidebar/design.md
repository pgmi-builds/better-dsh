## Context

- 上游专题一结论：布局反应性 CSS 化是**性能驱动的范式迁移**（删 observer/layout effect/几何读取），CSS 是构建期静态资产（CSS Modules），所有变体预渲染、由语义属性 + 选择器挑选；保留 JS 测量的仅限 CSS 表达不了的场景。
- 因此本 patch 的正确重做路线 = 加入静态 CSS 规则（或复用上游侧栏自带的响应式断点扩展），而非恢复 JS 测量——后者逆上游范式，下轮对齐还会再断。
- 与 loopback patch 共享"不在 dashr/src、落点待审计"的现状。
- user 实测症状（2026-09-03）：手势判定只含起点与距离——用户慢速按住拖选文本（复制等操作）被误判成滑动触发侧栏；真实滑动自带速率，与慢速按选可分。

## Goals / Non-Goals

- Goals：移动端右侧栏宽 0/隐藏；左右滑动手势恢复；patch 可随对齐重放。
- Non-Goals：不随 dashr 发布；不做通用移动端改造（仅侧栏隐藏 + 手势恢复）；不逆上游范式引回 JS 布局测量。

## Decisions

- **D1 CSS 路线优先**：media query（窄视口）或 container query 实现侧栏 `width: 0 / display: none`；若上游侧栏容器带语义属性（`data-*`），优先以属性选择器挂规则，随上游 DOM 语义演进的自然兼容性最好。
- **D2 手势恢复判定后置**：滑动交互失效可能是侧栏可见挤压布局的连带症状（侧栏隐藏后自愈），也可能是独立手势层问题——任务 3.2 在侧栏隐藏后复测再决定是否需要额外处理。
- **D2 手势判定三条件：起点 + 距离 + 速率**：滑动识别补速率门槛（pointer 序列的位移/耗时，达到阈值才算滑动）。慢速按选文本不触发、快速轻扫触发；阈值在真机调（正常轻扫的速率远高于慢速拖选，两者天然可分界，具体数值实测定）。侧栏隐藏后手势层是否还需处理（可能是挤压布局的连带症状）由任务 2.2 复测决定；速率门槛则属于手势层无论如何都要补的正确性修复。若上游侧栏自带手势识别器，先查它是否已有速率判定（有则只调阈值，不重造）。

## Risks / Trade-offs

- 上游侧栏的 DOM 结构/类名无稳定性承诺：规则尽量挂语义属性与结构选择器，少挂类名/哈希后缀。
